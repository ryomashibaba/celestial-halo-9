## 3. E5運用不具合：今回追加で確証を得た内容

### Windows作者処理

最初のローカル実行器が `Blender failed at author; exit ;` と表示したが、元の `author.stdout.txt` には実際のPNG2枚保存、BLEND保存、`Blender quit` が記録。stderrの `Material.use_nodes` は非推奨警告のみ。**実制作成功を、PowerShell実行器の空欄ExitCode判定が誤ってHOLDにした可能性が非常に高い。** その後の「BLEND header mismatch」は作者の `compress=True` を考慮しない回収ツールの不適切な非圧縮専用チェックによる可能性が高い。ファイル破損はそれだけで認定不可。Windows出力の存在をGitHubと混同しない。

### GitHub Actions（新たにジョブログを取得して事実確認）

GitHub E5 branch の実行 #42002438597／#42005012977／**#42005458650** は複数回失敗。最後の [#42005458650](https://github.com/ryomashibaba/celestial-halo-9/actions/runs/42005458650) では、`checkout`、R0B作者ソースSHA検査、Blenderのインストールが成功し、作者工程が実行された。しかしUbuntu配布Blenderが **OpenImageDenoiserを含まない**ため `RuntimeError: Build without OpenImageDenoiser` でレンダー失敗。途中でBLENDは保存された。その後、CI試行状態の保存コミットは生成されたが、研究ブランチに別コミットが入ったため、`git push` が `fetch first` で拒否された。

これにより、**「GitHub Actionsが起動していないかもしれない」という従来説明は訂正**する。起動・失敗は確認済み。CIが成功しなかったことをローカルWindowsの成功否定に使わない。失敗したCIを繰り返し修理することは現在の最優先美術制作ではない。必要時はその場で原因を確定して最小限修正（例：特定環境のデノイズ非対応、並列ブランチpush競合）し、手動の反復CIで利用枠を消耗しない。

## 5. 新計画の自家批判と最終修正（重要）

### 仮説A：NAVEだけ→H1だけを精密制作

- **利点**：最初の目標が狭くなり、1.65m視点から生活の有無を判断しやすい。
- **重大な欠点**：小さな現代住宅の密集と巨大な外殻不在を招き、Macro Impact Firstや「中央と周辺を相互改善」を損なう。R0Bはこの失敗に近い。
- **修正**：人間尺度2視点を早期の否定的ゲートに残しつつ、**同時に**中央の巨大質量・主要空洞・W0地形・高所都市への接続を都市俯瞰で検証する。最初から全域詳細を求めるのでなくマクロ構成の可視研究を維持。

### 仮説B：最初から約10km全域・30対象を一括自動制作

- **利点**：都市全体の統合・進捗を揃えられる。
- **重大な欠点**：不合格の箱・床・殻を30件へ大量複製し、AIの自由度と検証コストを著しく下げる。
- **修正**：**30対象台帳と都市マクロ空間は最初から維持し、実制作の集中対象は「中央・NAVE・H1・到達経路の一連の体験」1バッチ**。明確な美術の核が成立してから他地区へ横展開。初期の配置マーカーや粗い地形は完成と数えない。

### 仮説C：R0Bの同一BLENDを何回も直接修正する

- **利点**：既存アセットと比較カメラを活かし、同じ形状がどう変わったか実証しやすい。
- **重大な欠点**：出発点が現代的な家並みと水平梁で、改善の上限が低い。旧R1の移動案は衝突可能性も高い。2回修正したE2もART REJECTだった。
- **修正**：R0Bは**凍結した比較資料**とする。次の有望候補は独立BLENDで、都市的な造形言語自体を改める。候補の核が成立した後に**その新しい同一BLEND**を直接編集→再レンダーする。過去のE2/E5 BLENDを直接編集すること自体を目的化しない。

### 仮説D：ツール・CIを完全整備してから制作再開

- **利点**：技術的な取りこぼしを防げる。
- **重大な欠点**：E5の実測で、作者処理は成功していたのに補助スクリプトの不具合によって多数回のユーザー操作が発生した。Ubuntu GitHub Actionsのデノイザー失敗にも時間を使った。
- **修正**：**十分に成功しているWindowsの既存バックグラウンドBlender経路を優先**。ツールQAは破損・権限逸脱・実行できない重大障害に限定。必要時のみ小規模に修正。CI復旧を「美術バッチ前提条件」にしない。

### 仮説E：新しい巨大レンダー画像や文章を量産して突破

- **利点**：新しい形の発想材料になる。
- **重大な欠点**：これまでも綺麗なコンセプト画像から本物の3Dへ移ると単純化した。画像そのものは統一された実3Dを証明しない。
- **修正**：画像/スケッチは**実3D形状の具体的な問題箇所を指す美術参照**に限定。成果の中心は編集可能な真正BLENDと同一シーン多視点比較。

### 最終方針

**「一つの都市文明としての巨大尺度と人間尺度を両立した、強い造形上の核をまず真正Blenderで実証し、ART成立後に10km全都市へ接続・拡張する」**。

これはCITY MASTER 3D FIRSTの義務を緩めない。実制作の**順序と試行の品質ゲート**を改善するだけ。中央だけ完成・HERO4だけ詳細・他施設後付けの完成認定は引き続き禁止。

- 人間視点：歩いて入る公共入口、数百m級の吹抜けと多段公共室、生活街区の厚い断面、上層への視線先、低層/中層/高層の用途・動線を真正3Dで成立させる。
- 美術の単純化防止：単純な市場屋根、同型低層住宅の列、無地の巨大床、意味のない梁、外装だけの殻、都市機能のない記号をメイン造形にしない。飾りのための街区を建築の中核と誤認しない。
- 事前に小さな静止画の完成を承認したことにはせず、**Blenderで実3D化できる設計**を目指す。どこまでを1回のバッチで実現できるかはモデルや利用可能手段により変わるため、証拠のない実行時間・成功率は約束しない。

### 第2ゲート：真正Blenderで一つの大きな制作バッチを実行

- **既存不合格形状とは別の隔離候補**を新規BLENDとして作成。可能なら手続き生成は反復・部品配置・監査に限定し、主役形状は意図に従って自由にモデリングする。生成コードだけ大量に積み上げない。
- 初回は `human_public_interior`、`human_sky_district`、`urban_aerial` を同一3Dから取得し、美術面の弱さを早期に見切る。最初から視野外30施設の高解像度化に時間をかけない。
- 有望なら同じ新規BLENDを**保存複製して直接大幅修正**し、固定視点で前後比較。候補採択前には元の7視点（人間2、地上、都市俯瞰、中央正面・背面・東海側）を確認。1方向だけ良くてもHOLD。
- 短い技術判定は実BLEND生成、再読込、真正PNGの整合、視点・座標区別と保護条件のみ。技術PASSをART採用に昇格させない。
- ARTが明らかに不合格なら**その候補はREJECTし、新しい造形思想へ移る**。装飾・窓・照明で延命しない。形状が有望な場合だけ深掘り。

## 7. 美術評価基準：数字と画像の誤用をやめる

真正同一3Dの実画像から少なくとも次を審査：

1. **一目で唯一無二の異常な超未来文明か**。現代住宅、倉庫、駐車場、単純な駅屋根や汎用SF舞台に見えないか。
2. **都市級のマクロ主質量と本当に大きい公共空洞**があり、中央と周辺の序列・構造思想が多方向で読めるか。
3. **人がいる立体都市としての生活と公共用途**が、装飾アイコンではなく建築の断面・入口・階・公共動線の中に存在するか。
4. **複数高度の交通・接続・探索の目的地**が読め、街路の先が行き止まりの薄い棚ではないか。
5. 地形・人工内海・北山岳・西断崖・高所居住都市の間に**空間的関係**があるか。遠景と近景の美術が矛盾しないか。
6. 2視点だけのトリック・カメラ移動・暗さ・発光で主形状の弱点を隠していないか。**固定7視点**と必要な断面・近接ビューで審査。

メッシュ数、ARTレビュー枚数、CI成功数、GitHubコミット数、研究段階番号、勝手な合格点・%は正式美術成果の指標にしない。審査は具体的な見える問題を示し、**ART REJECT／候補HOLD／正式採用（ユーザー決定）**を分ける。
